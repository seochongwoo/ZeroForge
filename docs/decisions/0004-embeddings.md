# 0004. 임베딩: Voyage AI, 기록과 따로 저장, 필요할 때 만든다

- 상태: 채택
- 날짜: 2026-11-19

## 맥락

Step 8은 검색이 먼저다 (develop_plan Step 8). 서기가 참고할 과거 기록을 고르려면 기록마다 의미 벡터가 필요하다.
기록은 짧은 한국어 문장이고(2주 사용 기준 중간값 20자 남짓), 목표는 혼자 쓰는 도구에서 작은 제품까지다.

## 결정

- **공급사는 Voyage AI** (`voyage-3.5`, 1024차원). 모델 이름은 `EMBEDDING_MODEL`로 바꿀 수 있다.
  - 되돌려 받기(생성)는 Claude API로 할 예정이라, 그 단계부터 기록은 어차피 외부로 나간다. 그렇다면 검색 품질이 좋은 쪽을 고른다. 주석이 상투적일 때 가장 먼저 의심할 곳이 검색 계층이기 때문이다.
  - 공급사 호출은 `core/embeddings.py` 한 곳에만 있다. SDK 없이 표준 라이브러리로 HTTP를 직접 부른다(의존성을 늘리지 않는다).
- **`EntryEmbedding` 테이블에 따로 저장한다.** develop_plan은 "Entry에 embedding 필드"였지만, Entry는 불변이고 임베딩은 모델을 바꾸면 다시 만들어야 한다. 어떤 모델로 만든 벡터인지 함께 저장하고, 지금 모델과 다르면 다시 만든다.
- **기록끼리 비교하므로 모두 `input_type=document`로 임베딩한다.** 질문용 벡터를 따로 만들지 않아도 되고, 저장된 벡터를 그대로 질의에 쓴다.
- **쓰기 경로에서는 임베딩하지 않는다.** 검색할 때 빠진 것만 한꺼번에 만든다(`ensure_embeddings`). 공급사가 멈춰도 기록 저장은 늦어지거나 실패하지 않는다. 한꺼번에 미리 만들려면 `python manage.py embed_entries`.
- **검색 점수** = 의미 유사도 + 최근성(반감기 60일, 가중치 0.1) + 내가 같은 이름을 붙였는지(0.1). 의미가 먼저이고 나머지는 비슷할 때의 순서를 돕는다. 이 기록보다 먼저 쓴 기록만 본다. 과거가 없으면 빈 목록 (P3).
  - develop_plan의 세 번째 신호 "고정한 기록"은 고정 기능이 없어 아직 빠져 있다.
  - 지금 규모(수백 개 이하)에서는 인덱스 없이 정확 검색한다. 수만 개가 되면 HNSW 인덱스를 단다.
- 점수는 기록끼리의 거리일 뿐, 기록이나 나에 대한 평가가 아니다 (P1). `GET /api/entries/{id}/context`는 검색 계층을 실험하기 위한 것이고, 화면에 점수를 보여주지 않는다.

## 검토한 대안

- **서버 안 작은 다국어 모델** (ONNX, 약 200MB): 기록이 밖으로 나가지 않는다. 하지만 짧은 한국어 문장에서 품질이 가장 약하고, 사용자가 없어도 메모리 비용이 매달 나가며 이미지가 무거워진다. 생성 단계에서 어차피 외부로 나가므로 이점이 오래가지 않는다.
- **OpenAI 임베딩**: 저렴하고 무난하지만, 생성은 Anthropic이라 데이터를 맡기는 회사가 둘이 된다.

## 결과

- 운영에 `VOYAGE_API_KEY`가 필요하다. 없으면 검색 계층만 503이고 나머지는 그대로 동작한다.
- 가입할 때 입력 데이터를 학습에 쓰는지 설정을 확인하고 끈다. 제품이 되면 개인정보 안내에 "기록 내용이 임베딩·생성을 위해 Voyage AI와 Anthropic으로 전송된다"를 적는다.
- 로컬 Windows PostgreSQL에서는 일반 사용자가 vector 확장을 켤 수 없어, `setup_local_db.ps1`이 테스트 DB의 원본(template1)에도 켜 둔다.
